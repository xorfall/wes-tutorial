# 1. A first View

This chapter covers building a custom View with an agent: describing the
screen in a request, reviewing the package the agent returns, installing it in
a workspace and displaying a result with it. A **View** draws a workspace
value in its own way, for example a table with status colors, while the value
itself stays an ordinary result.

The example turns a snapshot of three services into a ServiceBoard: one row
per service with its status, requests per second and 95th-percentile latency.

## Prerequisites

- Chapters 1 and 2 of the main tutorial: calculations, names, records and
  lists.
- A running Wes client and a new workspace; see [Set up](../../README.md#set-up).
- For steps 2 and 3, an agent such as `claude`, `opencode` or `codex`,
  started inside a Wes Shell so that Wes connects its `wes_workspace` tools.
  The [setup reference](../reference/local-tools.md) lists the build tools and
  the launch steps.
- The agent is optional: the chapter ships a checked reference package, and
  [Run the programs](#run-the-programs) installs it without a model.

## Source, package, definition and instance

| Object | Where it lives | In this chapter |
| --- | --- | --- |
| **source** | files the agent writes | `view-work/service-board/` |
| **package** | one compiled, checked file | `view-work/service-board.wes-view.json` |
| **definition** | the installed package, in the workspace | `ServiceBoard` |
| **instance** | a definition bound to an input value | `$board` |

Each step is explicit. Writing source does not build a package, building does
not install it, and installing it does not draw anything until an instance
exists.

Paths in this chapter, such as `view-work/…`, are relative to the directory in
which Wes was started.

## Part 1: Request and review

### Step 1: The service snapshot

Enter [services.wes](services.wes):

```text
:calc pure {
  return {
    title: "Service monitor",
    services: [
      {name: "orders-api", status: "ok", rps: 120, p95Ms: 85},
      {name: "billing-worker", status: "degraded", rps: 40, p95Ms: 240},
      {name: "gateway", status: "down", rps: 0, p95Ms: 850}
    ]
  };
} > serviceData
```

```text
ok · kept
✓ $serviceData   { title: Text, services: List<{…}> }   2 fields
title       "Service monitor"
▸ services  List · 3 items
```

- `rps` is requests per second, and `p95Ms` the 95th-percentile latency in
  milliseconds. The values are synthetic; the snapshot describes no real
  service.
- `:calc pure` guarantees that the calculation calls no service (main
  tutorial, chapter 1).

### Step 2: The request to the agent

The agent receives the request in [assistant-task.txt](assistant-task.txt):

> Build a read-only ServiceBoard for $serviceData in the Wes design language.
> Show service, status, requests per second and p95 latency in milliseconds.
> Keep the input order. Show an empty message and report duplicate service names.
> Read the current View authoring guidance through Wes MCP before coding.
> Write the source in view-work/service-board, build and check the package,
> and return view-work/service-board.wes-view.json with the test results.
> Keep this first version static. Leave workspace installation to me.

- The request describes the data and the visible behaviour, not the code. The
  agent reads `$serviceData` and its type through its Wes tools.
- **MCP** (Model Context Protocol) is the connection through which the agent
  reads Wes tools and information. Its `view_authoring` tool supplies the
  current SDK declarations, the build workflow, the theme roles and a starter
  example. Reading it creates no files and installs nothing.
- The agent writes and compiles the files with its own local tools.
- Fonts and colors are not part of the request. A View uses the theme roles of
  Wes, so it follows the palette and density the reader has chosen.

### Step 3: The deliverable

The agent returns a source folder, a package and its check results:

```text
view-work/
  service-board/
    view.json
    types.yaml
    View.tsx
    view.css
    contract.ts
  service-board.wes-view.json
```

| File | Content |
| --- | --- |
| `view.json` | the identity (`name`, `id`), the renderer and the input type |
| `types.yaml` | the input type and its rules |
| `View.tsx` | the React component that draws the screen |
| `view.css` | layout styles of the package |
| `contract.ts` | generated by the compiler from the validated input type |
| `service-board.wes-view.json` | the compiled package that Wes installs |

Review the result for the four requested columns, the preserved row order, the
empty and duplicate cases, and a successful build and check. An agent's code
differs from the [reference source](service-board/View.tsx); the behaviour and
the checks are what count. The [package reference](../reference/package-files.md)
explains the files and the input rules of the reference.

## Part 2: Install and display

The animation shows steps 1, 4, 5 and 6 with the reference package. The agent
and the compiler are not recorded.

![WesDesk creating the service snapshot, installing the ServiceBoard package
with its digest, creating the board instance that draws a Service monitor
table with orders-api, billing-worker and gateway, and reading the instance,
which links back to it](01-first-view.gif)

### Step 4: Install the package

Enter [load.wes](load.wes):

```text
:package load path:"view-work/service-board.wes-view.json"
```

```text
ok
ⓘ installed view ServiceBoard · 8a09bab65fa592eb…
```

- The long hexadecimal value is the **digest** of the package: a fingerprint
  of its compiled content.
- Installing registers the definition and its input type in this workspace. It
  creates no instance and starts nothing.

### Step 5: Create an instance

Enter [create.wes](create.wes):

```text
:view create ServiceBoard input:$serviceData > board
```

```text
ok · kept
✓ $board   ViewInstance
Service monitor
Service health snapshot
Service          Status     Requests / s   p95 / ms
orders-api       ok                  120         85
billing-worker   degraded             40        240
gateway          down                  0        850
```

- `ServiceBoard` is the installed definition; `board` names the new instance,
  bound to `$serviceData`.
- The input is checked against the input type before the instance is created.
  `$serviceData` does not change.
- The cell draws the View: the rows keep the input order, and each status is
  shown as text and in a theme color.
- The View draws the value it was given. It does not fetch, poll or refresh
  anything.

### Step 6: Read an instance

Enter [read.wes](read.wes):

```text
:read $board
```

```text
ok · kept
✓ id1002   ViewInstance
→ $board · ServiceBoard   Go to view
```

The result refers to the existing instance instead of drawing it a second
time; `Go to view` moves to the cell of `$board`. On the command line, `:read
$board` prints the instance as JSON.

## Watch out

### The agent needs Wes tools and build tools

An agent started outside a Wes Shell has no `wes_workspace` connection and
cannot read `view_authoring`. Reading `view_authoring` does not install the
compiler or Node.js; follow the [setup reference](../reference/local-tools.md).

### Source files are not a View

Only a built and checked `.wes-view.json` file can be installed. A source
folder alone, or a package from an older build, is not the View in the source.

### Relative paths

`path:"view-work/…"` is resolved from the directory in which Wes was started.
Changing the directory of the Shell in which the agent runs does not move it;
use the absolute path the agent returns when in doubt.

### Input rules of the reference

The reference package accepts 0 to 16 services, a title of 1 to 128 Unicode
code points, and names of 1 to 64 code points. Status is `ok`, `degraded` or
`down`; `rps` and `p95Ms` are non-negative `Int` values. These rules are in
[types.yaml](service-board/types.yaml); chapter 4 of this series covers input
rules in detail.

- An empty `services` list shows `No services in this snapshot.`
- Duplicate service names show `Service names must be unique. Fix the input
  snapshot.` and no table. The input type cannot express uniqueness; the
  component checks it.
- An input that breaks a rule is refused when the instance is created:
  `:view create ServiceBoard input:$invalidData` with a status `unknown` and an
  `rps` of `-1` fails with `TYP005: View input does not satisfy
  ServiceBoardInput`, and its issues name `/services/0/status` and
  `/services/0/rps`.

### Exact numbers

The reference displays counters with `numericText`, which keeps the exact
digits of an `Int`. It never converts a large counter to a JavaScript `Number`,
which would round values above 9007199254740991.

### Failures in this chapter

| Message | Cause |
| --- | --- |
| `TYP005` View input does not satisfy ServiceBoardInput | an input that breaks a rule of the input type |
| `No services in this snapshot.` (in the View) | an empty `services` list |
| `Service names must be unique. Fix the input snapshot.` (in the View) | two services with the same name |

## Run the programs

`services.wes`, `load.wes`, `create.wes` and `read.wes` contain steps 1, 4, 5
and 6. `check.py --preview` builds the reference package, starts Wes on a
temporary data home and prints its address; enter the four programs there. It
calls no model, and <kbd>Ctrl</kbd>+<kbd>C</kbd> stops the server and removes
its files:

```sh
python3 custom-views/01-first-view/check.py --preview
```

Without `--preview`, the check builds the package in a temporary folder and
verifies the installation, the instance, the input rules and their limits, the
rendered component, and the text of this chapter:

```sh
python3 custom-views/01-first-view/check.py
```

```text
PASS first View: build, check, load, create and read
PASS edge cases: empty, duplicates, invalid, limits and exact numbers
```

## Summary

| Command or term | Effect |
| --- | --- |
| `view_authoring` | the agent's tool for current View authoring guidance |
| `:package load path:"….wes-view.json"` | install a checked package as a definition |
| `:view create Name input:$value > name` | create an instance; the input is checked |
| `:read $instance` | refer to an existing instance |
| source, package, definition, instance | the four stages of a View |

## Exercises

1. Which of `service-board/`, `service-board.wes-view.json`, `ServiceBoard` and
   `$board` exist only inside the workspace?
2. Does showing `$board` again obtain new measurements of the services?
3. A teammate adds a fourth service with the name `orders-api`. What does the
   board show?

<details>
<summary>Answers</summary>

1. `ServiceBoard`, the installed definition, and `$board`, the instance. The
   source folder and the package are files.
2. No. The View draws `$serviceData`, a value that was entered once. This
   version neither queries nor polls.
3. `Service names must be unique. Fix the input snapshot.` and no table.

</details>
